# 对话反模式

## 1. 让用户操作内部文件

错误：要求普通用户自己编写 batch JSON、幂等键或 labels 文件。

正确：对话中收集目标和选择，由 Agent 在后台创建与保存这些证据。

## 2. 未报价就把“想做图”当成批准

错误：用户刚说目标就直接执行 `run --approve`。

正确：先展示创作确认卡、张数和生成调用数；用户明确同意当前轮次后执行。

## 3. 沿用上一轮批准

错误：第一次批准了 6 张，优化出 2 张后自动生成。

正确：展示“下一轮 2 张、2 次调用”和修改摘要，重新取得批准。

## 4. 把沉默当作整组批准

错误：用户只评价第 3 张，就把其余图片全部标为 approved。

正确：只记录用户明确表达的标签；未提及图片保持 unlabeled。

## 5. 把模型建议当成人工决定

错误：建议分高于阈值后直接宣布整组已批准。

正确：说明确定性门禁与建议分，等待用户说“整组批准”或给出单项决定。

## 6. 用笼统反馈编造改写

错误：用户说“不太好看”，系统自行更换人物、配色和构图。

正确：追问一个可观察差异，例如“想调整配色、人物、构图还是文字？”再创建新 prompt。

## 禁忌清单

- 不隐藏会新增的生成调用数。
- 不重做已经获批的图片。
- 不覆盖上一轮计划或图片。
- 不索取密码、Cookie 或 API Key。
- 不把图库案例、模型建议或进程退出码冒充最终验收。

## 计划改变后沿用旧批准

错误：用户改了 prompt 或换了参考图，Agent 说“上次已经批准过，直接生成”。

正确：计划一旦改变，上一张卡的批准失效。重新校验计划、重新出卡、重新报告轮次和剩余
生成调用数，取得新的同意后才执行。

## 用“再跑一次”排查中断

错误：用户问“上次怎么停了”，Agent 回答“我再跑一次看看”。

正确：先读台账，再执行 `recover`（它不调用任何生成），据此说明已完成、失败、未尝试和
未决各几项，并给出唯一的合法下一步。未决项可能已经产生过调用，重复运行会再扣一次费。
